# **Драйверы оценки**

В рамках подготовки коммерческого предложения по реализации IT-функционала требования зачастую поступают с разным уровнем детализации — от одностраничного брифа или аудиозаписи звонка до технического задания на 120 страниц. При этом сроки подготовки ценового предложения достаточно сжаты, а возможности дебрифинга клиента ограничены несколькими встречами и небольшим опросником.

Несмотря на эти ограничения, технической команде необходимо достаточно точно оценить проект. Для этого применяется методика оценки на основе драйверов оценки. 

**Драйвер оценки** – параметр или признак, характеризующий отдельный аспект работ по проекту существенно влияющий на и используемый для оценкуи объёма трудозатрат, необходимых материалов и стоимости реализации. Должен быть выражен в числовой, логической или категориальной форме. Примером числовой формы могут быть – количество-во интеграций; логической – необходимость подготовки закрывающей документации по ГОСТ; категориальной – требуемая степень зрелости и уровень проработки сложность бизнес-логики (прототип - простая, MVP - средняя, продакшн - сложная).

ВФокусировка на выявлениеи драйверов оценки, как показывает практика, помогает обнаруживать слепые зоны в требованиях и формулировать вопросы к клиенту, которые за минимальное количество ответов действительно позволяют снизить неопределенность и качественно проработать подготовить предварительное коммерческое предложение. Кроме того, драйверы помогают обосновывать оценку перед заказчиком, делая ценообразование более прозрачным и конфигурируемым.

Важно разделять драйвер оценки и саму оценку: это разные сущности. Построение функции стоимости проекта на основе значений драйверов оценки — отдельная задача.

ЗВ этом смысле задачу выявления драйверов оценки можно рассматривать как аналог задачи feature engineering/feature selection для предсказания цены: необходимо определить набор признаков, которые наиболее существенно влияют на трудоёмкость и стоимость реализации проекта.    
Удобно ввести понятие "**пространство работ**" – полный набор типов работ, который может возникнуть в проектах данного класса. И дальше придерживаться правила: каждая значимая область пространства работ должна иметь хотя бы один драйвер, через который можно описать её масштаб.

**Примеры драйверов для DWH-проекта:**

| Область работ | Драйвер оценки |
| ----- | ----- |
| Интеграции | Количество интеграционных потоков и объектов загрузки |
| Модель данных | Количество сущностей модели данных |
| Трансформации и бизнес-логика | Количество независимых расчётов и бизнес-правил (порядки), часто выражено в доменах и предметных областях |
| Витрины данных | Количество витрин данных |
| Потребление данных | Количество отчётов, выгрузок, API и других интерфейсов |
| Data Quality | Уровень сложности требований к проверке качества данных |
| Оркестрация | Количество независимых процессов / workflow |
| Информационная безопасность | Уровень требований ИБ |
| Документация | Уровень требования к составу и глубине документации |
| Миграция | Количество мигрируемых объектов |
| Тестирование | Уровень необходимого тестирования |

В рамках ML/AI проектов список очевидно должен быть скорректирован. Например, из того что пришло быстро в голову:

* степень качества данных  
* необходимость разметки данных  
* требуемая точность решения  
* доступность API LLM моделей от зарубежных вендоров  
* и др.
